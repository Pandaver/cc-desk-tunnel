# 代码审查留下的事项（2026-10）

2026 年 10 月对整个项目做了一次复查。当时就能定的已经改掉，这里记的是需要先讨论、或者暂不处理但值得知道的事项，供以后动到相关部分时参考。编号沿用复查时的顺序，中间缺的是已经处理的。

没有逐行读的部分：统计与升级模块、各设置与统计面板、样式表、打包脚本；它们只按模式排查过。

标记：【待议】需要先讨论再动；【记录】暂不处理，留作背景；【已做】后来已经处理。

## 一、架构层面

1. 【记录】归属模型现在是一致的，值得保持：需要 CLI 持续工作的东西（运行、审批）归设备，
   随连接存在的交互流（终端、登录流程、状态读取）归连接。这条规则比“全部归连接”或“全部归设备”都简单，
   以后新增功能按它归类即可。
2. 【待议】`activeRun.connectionId` 和 `run.status.connectionId` 已经没有读者（客户端改按设备判断），
   只剩记录意义。下次协议版本变动时可以去掉，或改成设备标识。
3. 【待议】每条连接的隧道仍有自己的监听端口和配置目录，现在只有就绪探测在用；真正的命令都走设备入口。
   可以让探测也走入口，隧道不再监听，少一个端口、一份配置和一条为探测而开的共享连接。
   改动在 `tunnel.ts`，要重跑隧道相关的全部测试，收益是结构更简单，不是功能。
4. 【待议】模拟模式的分支散在服务端各处：`server.ts` 里有 32 处 `options.claude` 判断。
   更干净的做法是把“运行一轮”抽成一个接口，模拟与原生各实现一份。动手前要先确认模拟模式还要保留多久：
   安装版客户端已经没有模拟入口，它只服务于开发和界面测试。
5. 【记录】重连放在渲染进程（`client.ts`），连接桥每次重建。另一种做法是让连接桥自己重连、渲染进程无感。
   没有选它的原因：重连后本来就要重新订阅和补历史，这些状态在渲染进程；连接桥保持一次性更容易推理。
   三处心跳（服务端对客户端、连接桥对服务端、每条通道）各管一段，不重复。
6. 【记录】事件落库加序号是接续能做得轻的根本原因，终端是唯一不在其中的流。
   维护者已确认终端随连接结束是合理的，不再处理。

## 二、代码结构

7. 【待议】`apps/server/src/server.ts` 1349 行，是一个 1220 行的闭包，内含 34 个函数：
   接入与认证、限速、设备席位、会话命令、运行、终端、账号、升级的接线全在一起。
   建议按职责拆成几个模块（接入与席位 / 运行 / 终端 / 账号 / HTTP），闭包里共享的状态收成一个对象传递。
   纯搬动，不改行为，但面大，应当单独一个 PR，并在 0.2.12 稳定之后做。
8. 【待议】`apps/desktop/src/App.tsx` 1508 行，一个组件里 25 个 `useState`、18 个 `useEffect`、约 30 个内部函数：
   登录与连接、项目列表、各类菜单、快捷键、会话操作都在里面。
   建议抽成几个 hook（连接与登录、项目与会话操作、菜单定义、快捷键），页面骨架留在 `App`。同样是纯搬动、单独 PR。
9. 【待议】`apps/desktop/src/style.css` 2912 行单文件，只有 10 个分节注释。按组件拆文件能让改样式时不必通读，
   但要确认层叠顺序不变；可以和第 8 项一起做。
10. 【记录】其余文件规模正常：没有发现拆得过细、来回跳转的模块；`electron/` 下 `.cjs` 入口加 `.mjs` 模块的分工清楚；
    协议集中在一个包里，两端共用，边界清晰。测试文件偏长（`server.test.ts` 928 行）但按用例平铺，可读。
## 三、缺陷与隐患

16. 【待议】断线超过一分钟但不到宽限期时，Claude 每条命令都会等满一分钟再失败。它若一直重试，
    会在离线期间持续消耗额度（每次失败是一轮模型调用）。可选做法：入口在设备离线期间让命令一直等到宽限期结束，
    或在提示词里说明这种失败的含义。需要先看真实使用里 Claude 的表现再定。
17. 【记录】客户端每 32 毫秒合并一批流式事件时，对整段事件重新排序并重算对话结构。
    会话在内存里只保留分页后的一段，目前没有观察到卡顿；极长的单轮输出可能是个热点，出现时再优化。
18. 【记录】重连期间连接桥关闭会短暂取消“保持唤醒”，下一次尝试又恢复。离线时间长时系统可能进入睡眠，
    而睡眠本身就会断网，影响可以忽略。

## 四、安全

19. 【记录】设备入口没有扩大攻击面：它与隧道一样只监听容器内的回环地址，连上它的进程仍要持有当次连接的私钥才能通过设备的 SSH 认证；
    私钥每次连接更换，文件权限 0600，用原子替换写入。入口最多挂起 32 条等待的连接。
20. 【记录】设备标识由客户端自报，持有服务凭据的人可以自称任何一台设备并接手它的运行。
    这在单用户模型下是成立的（凭据即全部权限），但如果以后做多用户，设备标识需要由服务端签发。
21. 【记录】未登录连接的名额是每个来源地址 4 个、全局 64 个。多条执行通道同时建立时客户端会退避重试，实测未触及上限；
    经反代时依赖 `X-Real-IP` 区分来源，这一点文档已说明。
22. 【记录】凭据比较用常量时间；`leave` 帧只在认证之后才被接受，只影响发送者自己那台设备。

## 五、存储与性能

25. 【已做】事件库按“每个流式片段一行”保存，几十轮对话的库就有几十 MB。现在片段只转发，一段输出结束时存一条；
    旧库在升级后第一次启动时合并一次，合并前留整库副本和说明。
26. 【已做】每写一条事件都读出并校验整份会话元数据。现在元数据在内存里留一份。每次提交仍同步磁盘：
    写入次数已经少了一到两个数量级，不必为此放宽断电时的持久性。
27. 【已做】`userMessage()` 用 JSON 字段在一个会话的全部事件里查重，没有索引。行数减少后不再是问题，未加索引。
34. 【待议】界面历史里占主体的内容（文字、思考、工具调用与结果）在 Claude Code 自己的会话记录里也有一份。
    下一步评估能否直接从原生记录读历史，本库只存原生记录里没有的东西（审批、运行状态、送达回执、项目与设备绑定、
    用量读数）。要先弄清：原生记录在压缩、分叉、清理之后还剩什么；按页读取和游标怎么对应；模拟模式与没有原生记录的旧会话怎么办。

## 六、其他

29. 【待议】版本号的来源：服务端读的是 `apps/desktop/package.json` 的版本，根目录和服务端包的版本都是 0.0.0。
    两端同版本是既定规则，但“服务端的版本写在客户端的包里”不直观，发布、打包、入口脚本各自去读这个文件。
    可以把版本放到根 `package.json`，其余位置由它生成。纯整理，不急。
30. 【已做】本机的持久化分散在几处，分工已写进 `apps/desktop/README.md`。
31. 【记录】主进程的 IPC 边界是好的：只应答自己的页面，外链有域名白名单，写文件都经系统对话框，粘贴图片限制类型与大小，
    没有暴露执行命令的入口。渲染 Markdown 用 `react-markdown` 且未启用原始 HTML。
32. 【记录】容器以普通用户运行、去掉全部 capability、禁止提权，传给 CLI 的环境变量在启动时清掉了服务自身的密钥。
    镜像里装了一套开发工具（编译器、python、git 等）给 CLI 使用，体积因此较大，这是有意的。
33. 【记录】提示词里仍写着“设备离线就如实说明、不要回退到本机”。配合断线接续，这意味着离线超过一分钟时 Claude 多半会停下来汇报，
    而不是无限重试（第 16 项担心的额度消耗因此有限），代价是需要使用者回来点“继续”。是否改提示词与第 16 项一起决定；改动会让提示缓存失效一次。
