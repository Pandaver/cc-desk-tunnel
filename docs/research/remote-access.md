# 人不在开发机前时：远程操作与无头执行端的三条线路

2026-10-14，起因是 [#70：桌面客户端新增实验性 Web 工作台](https://github.com/sun168567/cc-desk-tunnel/pull/70)。本文既记录目前的取向，也保留问题是怎样被重新表述的、过程中比较过什么、哪些联想值得以后接着想。研究不只需要最后的答案；省掉推导，过一段时间很容易再次走一遍相同的弯路。

依据：对照主线 `5fc6d1b` 的设备、会话、执行通道与界面实现，重点阅读 #70 的 `19b523b` 中连接汇聚、Web 鉴权、宿主适配和调度改动。**这是设计研究和重点代码阅读，不是对 #70 的完整安全审计；本次没有运行其 Web 功能，也没有实现三条线路。** 作者报告的人工验收与本文亲自验证的事实分开看。后续提交需要重新核对，本文描述不自动适用于更新后的代码。

## 目前收敛到哪里

1. **线路 1：让另一台客户端经现有服务端操作 B，优先推进，欢迎一起实现。** “其他设备”里区分设备状态，直接继续留在 B 上的会话，并逐步支持为 B 新建会话。会话不迁移，项目也不复制。
2. **线路 2：让 B 可选开放 Web 控制入口，认可方向，与线路 1 互补。** 希望 #70 作者先把实现、边界和回归补完再合；来不及可以积累一段时间。不能先合一个会改变原有客户端内部行为的版本，再靠后续补丁把边界补回来。
3. **线路 3：将 B 做成无头 Linux 客户端，作为后续方向。** A 跑 Claude Code，B 放项目与工具链，C 是实际操作的客户端。B 优先接受线路 1 的控制，也可以选配线路 2 的 Web 入口。

这里认可的是方向，不是对 #70 当前提交的合入批准，也不是三条线路已经排好工期。线路 2 不必等待线路 1 全部完成，但要独立满足自身的合入条件；线路 3 优先建立在线路 1 上。

## 从问题到三条线路

### 第一步：先弄清到底在远程操作谁

最初看到“Web 工作台”，容易理解成给服务端做网页。#70 实际做的是：桌面客户端自己托管网页和 Web 后台，浏览器操作这个客户端，再利用它已有的连接驱动远端 Claude Code。

为避免“服务端”和“客户端”随着观察角度变化而混淆，本文固定三个角色：

| 角色 | 放在哪里、做什么 | 哪些东西属于它 |
| --- | --- | --- |
| A：agent 运行端 | 运行服务端和未修改的 Claude Code | 原生会话、上下文、模型调用与调度 |
| B：项目执行端 | 现在通常是安装桌面客户端的开发机 | 项目文件、Git、编译器、shell、执行通道 |
| C：人的操作端 | 手边的另一台电脑、手机或平板 | 查看进度、输入指令、处理审批的界面 |

原有使用方式把 B 与人的操作端合在一起。人离开 B，就要远程桌面回去。真正的需求是：**A 继续运行 Claude Code，重开发任务仍落在 B，人可以从 C 继续指挥。**

这里的 C 是同一使用者自己的另一个入口。“第三方远程操作”容易让人联想到向陌生人开放服务，不是本项目的目标。拿到控制凭据的人具有相应控制权，但这不等于项目要建设多用户协作或租户隔离。

### 第二步：网页由 A 提供，还是由 B 提供

曾比较过两种想法：

- B 提供网页，就是 #70 的方向。它掌握本机项目、附件和定时任务，复用现有客户端最直接；代价是 B 新增监听入口，C 必须能访问 B。
- A 提供网页，C 直接访问 A，表面上链路更短，也容易利用 A 已有的可达地址；但 B 上的项目目录、附件、定时任务和本机操作并不会自动变成 A 的能力，需要定义跨设备接口。

这个比较有启发，但不是当前的二选一。**“网页放 A 上”不等于下面的线路 1。** 线路 1 的 C 仍是已有客户端，只是允许它经 A 指挥 B。把网页移到 A 是另一个需要单独评估的服务端 Web 方案，目前没有决定采用。

还有一个容易混淆的编号：#70 原文的“两条路线”是未来中继的独立部署与合并部署；本文的线路 1、2 是两种控制入口，所讨论的层次不同。

### 第三步：从“再造远程入口”转向“用好其他设备”

现在 C 已经能看见 B 的会话。既然 A 同时知道多台设备，会话也记着项目在哪台设备，为什么必须先把会话接管到 C 才能继续？人只是换了输入位置，开发环境并没有换。

由此产生线路 1：把“谁下指令”和“指令最终在哪执行”分开。“其他设备”也应从历史会话分组，逐步变成能识别设备在线情况、知道是否可操作的入口。

这个方向与 Web 不冲突。另一台已装客户端的电脑适合线路 1；手机、平板或临时浏览器适合线路 2。二者都在解决操作位置的变化，只是入口和可达性条件不同。

### 第四步：Web 应当是客户端管道的外接入口

对线路 2 的进一步要求是：浏览器看到的业务能力应尽量是客户端的一比一映射。桌面与 Web 共用业务实现，Web 只承担认证、传输、页面承载和必要的宿主差异适配。

“一比一”不是把任意 Electron IPC 暴露到网络，也不是把窗口最小化、安装器、开发者工具做成远程功能；它要求**同一项业务操作有同一个实现、同一种结果和错误语义**。无法映射的本机能力应明确列出，并提供合理替代或暂不开放，不能悄悄换一种含义。

因此，“轻量”首先指结构和维护负担，不是硬性限定几百行代码。新增 Web 认证和传输代码有合理成本；让每项桌面业务从此都维护两套状态机，或者为了 Web 改写所有桌面连接的生命周期，则不是轻量外延。

### 第五步：既然操作界面可以搬走，B 为什么一定需要桌面

线路 1 与线路 2 都把“人的界面”从 B 上拆开了。接着自然想到：B 可以是一台常开的 Linux 机器，只保留项目环境、连接和执行能力，不安装图形桌面，也不要求显示器和登录着的桌面会话。

这就是线路 3。不是另开一套 agent 服务，也不是把 A 的 Claude Code 搬到 B，而是让现有 Linux 客户端拥有无界面的运行形态。A、B、C 可以部署在不同机器；同机部署只是可选拓扑，三个角色仍应分清。

## 场景是否值得做

以下频率是针对本项目用户的产品判断，没有调查数据，不作为普遍统计：

| 场景 | 需求强度判断 | 更合适的入口 | 必须保留的体验 |
| --- | --- | --- | --- |
| 办公室开发机开着，回家从笔记本接着做 | 在多设备开发者中较高 | 线路 1 | 不搬项目、不改会话归属，不要求笔记本装全套工具链 |
| 离开座位，用手机看进度、审批、补一句话 | 有价值，偏轻操作 | 线路 2 | 小屏可用，审批结果同步，浏览器关闭不结束任务 |
| 临时借用一台没有客户端的机器 | 相对较低 | 线路 2 | 独立授权、退出和撤销；不把 A 的服务凭据交给浏览器 |
| Linux 工作站、家用服务器或云机器常年做编译和长任务 | 对有此环境的人价值高，普及程度待观察 | 线路 3 + 线路 1 | B 常驻、C 随时离开；重连和故障状态可理解 |
| 需要完整 IDE、图形调试或任意桌面软件 | 超出上述轻控制目标 | 继续使用已有远程桌面或开发工具 | 不把本项目扩成通用远程桌面 |

会话留在 B 与“在本机继续”是两项不同功能。前者只是远程操作 B，后者将执行目标切换到 C；原有接管、分叉仍有价值，界面应让人明确选择，不能把两种行为合成一个模糊的“继续”。

## 线路 1：经 A 操作其他客户端

### 实现基础与缺口

```text
C 的客户端 --控制消息--> A：Claude Code
                            |
                            +--现有执行通道--> B：项目与工具链
B 的客户端 --连接/执行通道--> A
```

C 与 B 都主动连接 A。只要二者能访问同一个 A，C 就不需要直接访问 B；A 不一定在公网，也可以在双方都可达的私有网络。不能把“已有服务端”直接等同于“天然公网可达”。

主线已经按运行的设备选择执行通道，关键不是再造执行协议，而是明确控制权和执行归属。对应代码见 [server.ts](../../apps/server/src/server.ts)、[消息契约](../../packages/protocol/src/index.ts)、[Sidebar.tsx](../../apps/desktop/src/Sidebar.tsx) 与 [App.tsx](../../apps/desktop/src/App.tsx)。

| 环节 | 当前实现 | 建议变化 |
| --- | --- | --- |
| 发消息、继续、压缩 | `onDevice` 要求操作设备与会话设备相同；新运行取发送者设备 | 执行目标取会话归属 B，检查 B 的执行通道 |
| 运行中追加输入 | 另有 `active.device` 与发送者的比较 | 与新建运行一致授权，不能只改第一条消息 |
| 审批、停止、结束后台任务 | `controlRun` 限定运行设备 | 允许同一服务授权范围内的其他控制端；重复和过期操作返回明确结果 |
| 新建会话 | `session.create` 使用发送者设备 | 增加明确的目标设备，路径按 B 的系统解释与校验 |
| 在线状态 | 会话保存设备身份；协议没有完整的设备在线快照 | 由 A 提供设备状态快照与变化事件，重连后可恢复 |
| 执行 | `seats.get(run.device)` 选择通道 | 沿用此方向，不因为 C 发消息就变为 C 的通道 |

原生终端首阶段可以保留现有限制。理由是它还涉及连接归属、输入流、流量控制和关闭行为，不能因为普通消息可远程发送就直接放开；并不是“终端在原理上只能本地交互”。后续远程终端要明确控制连接与执行设备各自负责什么。

### “其他设备”里的状态应表达什么

建议至少区分以下状态；内部字段、命名和保留时间仍待实现设计：

| 状态 | A 知道什么 | 界面与操作 |
| --- | --- | --- |
| 在线且可执行 | B 的控制连接和执行通道都就绪 | 可以继续 B 的会话 |
| 已连接，执行通道未就绪 | 能收到 B 的控制消息，但不能执行 | 显示“准备中”或故障原因，不能假装已经可用 |
| 暂时断开，等待重连 | A 还在为 B 保留运行 | 保留历史和进度，显示等待；新任务不盲目排队 |
| 离线 | 当前没有可用通道 | 可以查看已有会话，不能发送需 B 执行的新任务 |
| 状态未知 | C 刚连接，或状态同步尚未完成 | 不把缺失数据当成离线，也不乐观允许发送 |

在线状态应来自 A 对连接和通道的观察，不能拿“有历史会话”“最近有消息”代替。C 重连时需要完整快照，B 上下线时需要更新；若要显示没有会话的新设备，还需要设备清单，不能只从会话列表反推。

项目也存在类似问题：A 现在能从历史会话看到 B 的已用路径，不代表知道 B 的完整项目列表。第一阶段可以从已知项目创建，并由 B 校验目录仍存在；远程浏览目录、选择全新项目属于后续能力，不能无意间用 C 的本地路径选择器。

### 并发、断线和信任

同一使用者的多个入口可以共同操作，但“沿用现有机制”不能替代验证：

- B 与 C 同时发送时，继续使用单会话运行与追加输入机制，确认顺序、请求去重和响应归属；超时不自动重发有副作用的请求。
- 同一审批可以在多个入口显示，但只能被有效处理一次。后来的回答应看到已处理状态，不能误报成功，也不能影响下一轮同名审批。
- C 断开不应结束 B 的运行。B 断开才影响执行；现有约 5 分钟宽限是默认配置，不是发送排队保证，主动退出与意外掉线也不同。
- B 离线时，A 仍可能处理停止等控制操作，不应简单将所有按钮一律禁用。新任务、追加输入、审批在此时是否允许，要逐项写清，首阶段避免新增隐式队列。
- 不能让 C 的设备身份、操作系统或路径覆盖 B；否则会话虽未“接管”，实际执行环境却被改错。

线路 1 不新增监听入口，但**确实扩大了其他已授权连接可执行的操作范围**。现有单用户服务凭据是高权限凭据，设备 ID 由客户端报告，不是独立的安全身份；这不是省略授权检查的理由。仍要验证未认证连接不能读取或控制，不能跨服务混用设备，不能靠任意目标 ID 绕过状态校验。此次不顺带建立多用户权限系统。

会话不换设备意味着不需要因换机器追加环境变化说明，有利于保持原有上下文；不能由此保证模型侧提示缓存必然命中，缓存还受服务方行为、时长与其他内容变化影响。

### 工作量和推进方式

此前曾粗估“服务端 50–100 行、客户端 200–300 行”。那只覆盖放宽部分设备检查和显示输入框，没有计入设备清单、快照同步、远端项目、并发审批和完整回归，不适合作为交付承诺。

更合理的拆分是：先把设备状态显示做准确，再打通已有 B 会话的远程控制，之后增加为 B 创建会话。涉及服务端、协议和客户端三处，复杂度中等，主要难点是生命周期与并发一致性。新增协议字段或事件需要按现有严格校验和版本机制协调升级，可与其他确定的协议改动一并发布，但不预先绑定某个尚未定稿的 PR。

这一条可由维护者推进，也欢迎 #70 作者一起做。Web 的多视图经验有参考价值，但不能为了复用而强行把服务端设备控制与 B 内部浏览器转接合成一层。

## 线路 2：B 开放可选的 Web 控制入口

### 目标与边界

```text
C 的浏览器 --独立 Web 鉴权--> B：可选 Web 适配层
                                  |
                                  +--现有客户端能力--> A：Claude Code
                                  ^                       |
                                  +------现有执行通道------+
```

Web 依托 B 运行，复用桌面页面与业务逻辑。设置提供开关、监听端口和授权管理，默认关闭；默认回环监听，局域网访问另行显式开启。密码或配对码是交互选择，认证、会话管理使用成熟做法，不另创认证协议。

**Web 不负责让 B 在外网可达。** 它只提供一个可访问的端口；路由、防火墙、组网或反向代理由使用者安排。可以说明接入已有安全网络的方法，但不把公网中继、自动开防火墙或额外服务部署列为此 PR 的完成条件。#70 原文所提中继可以另行研究。

同样，不应把“局域网”视作加密或可信的保证。当前明文 HTTP 的适用边界要明确；跨不可信网络需要受保护的传输。是否内置 HTTPS、如何配合现有 HTTPS 终止点，可再定实现方式，不以自建证书管理平台为前提。

### “客户端内部没变”怎样落实

这里要求的是桌面核心业务、执行通道和生命周期不因 Web 的存在而改变，而不是机械要求原文件一个字也不能改。为了增加宿主接口做少量等价整理可以讨论；影响桌面核心的重构必须独立说明和验证，不能混在 Web 功能里默认通过。

| 情形 | 应保持的性质 |
| --- | --- |
| 从未开启 Web | 桌面仍走已有核心连接与执行逻辑；不因 Web 增加核心握手依赖、观察连接或调度要求 |
| 开启、关闭、更换 Web 监听端口 | 仅改变 Web 入口；不中断 B 到 A 的连接，不结束已有运行 |
| 浏览器刷新、关闭、掉线、会话失效 | 只清理该浏览器的资源；不能对整个设备发出离开语义 |
| 多个浏览器与桌面同时在线 | 各自选择会话，共享业务状态；一次操作只执行一次 |
| 桌面原有断开、退出与异常重连 | 保持已定义的行为，不暗改“退出是否停止运行”等语义 |
| 定时任务 | 只有 B 的既定调度者自动触发；浏览器不是第二个调度器 |
| Web 启动失败、认证数据损坏、端口占用 | Web 报错并保持可理解状态，不能拖垮普通桌面使用 |

“页面关闭”与“主动断开设备”尤其要分开。Web 多视图确实带来新需求，但新增浏览器入口不构成改写已有桌面退出契约的理由。

### 对 #70 当前实现的具体观察

它已有值得保留的基础：共用前端构建、浏览器宿主接口、独立配对、服务会话标识哈希存储、操作白名单、来源检查、请求与连接限制，以及避免浏览器重复自动调度的处理。PR 报告约新增 3042 行、删除 143 行、涉及 33 个文件；这是评审面的提示，不是单凭行数否定实现。

不过，以下几项与合入要求之间仍有距离：

1. **关闭 Web 仍会改变桌面连接路径。** 该提交的 `main.cjs` 在 `proxy:connect` 中无条件创建 `createControlHub` 和 `openControlEndpoint`，桌面拿到的不再是原来的 `bridge.url`。`control-hub.mjs` 增加主连接、每个视图的观察连接、请求映射与终端分发；同配置重连会复用汇聚层。这不自动证明发生了 bug，但证明改动不只是可选 Web 外接入口。“没有修改服务端和协议”不能证明桌面内部没有变化。应优先收敛到既有业务能力外接，必要的公共重构独立评估，并提供关闭与开启两种状态的等价性证据。
2. **浏览器授权缺少服务端到期判定。** `web-auth.cjs` 用会话标识的哈希映射到 `true`，没有创建、最近活动或到期时间；关闭入口、重启或改变端口也不自动撤销授权。需要明确有效期、退出、全部撤销和在线连接失效语义。30 天无活动失效只是讨论示例，不是已经敲定的常数；Cookie 到期不能代替服务端拒绝过期凭据。
3. **“只存哈希”必须说准对象。** 当前哈希保存的是浏览器会话标识；配对码本身与元数据一起持久化，可用时由系统秘密存储加密，否则退回私有文件。不能笼统写成所有秘密都只存哈希。若选用户自设密码，应使用适合密码的成熟存储与验证方案，而不是照搬高熵随机令牌的处理。
4. **调度仍与桌面渲染页有关。** `schedules.ts` 区分远端视图并发布调度快照，避免浏览器自动触发任务是正确方向；但页面重载、调度者退出、浏览器手动运行以及不同时区下的显示和结果语义都要验证。它也说明线路 3 不是去掉窗口就能完成。
5. **验收需要可复现。** PR 描述有 Web/Electron 专项及真实环境验收，但本次提交没有把专项测试纳入仓库。应提交关键自动回归和必要夹具，说明真实验收覆盖的平台、浏览器、部署方式与仍未覆盖部分。作者的验收报告有参考价值，不等于维护者已经复测。

这些反馈针对上述固定提交，定位入口可见[该版 main.cjs](https://github.com/sun168567/cc-desk-tunnel/blob/19b523b340e6187cffb82caec73decae327de57a/apps/desktop/electron/main.cjs)、[control-hub.mjs](https://github.com/sun168567/cc-desk-tunnel/blob/19b523b340e6187cffb82caec73decae327de57a/apps/desktop/electron/control-hub.mjs)、[web-auth.cjs](https://github.com/sun168567/cc-desk-tunnel/blob/19b523b340e6187cffb82caec73decae327de57a/apps/desktop/electron/web-auth.cjs) 和 [schedules.ts](https://github.com/sun168567/cc-desk-tunnel/blob/19b523b340e6187cffb82caec73decae327de57a/apps/desktop/src/schedules.ts)。

### 怎样算业务映射足够完备

不要求第一版覆盖每个操作系统细节，但要有一份明确的能力对照，关键工作流程闭环。故意缺失的能力不能靠按钮失效或模糊报错来表达。

| 能力 | 映射原则与需核对的边界 |
| --- | --- |
| 会话、消息、审批、停止 | 调用同一业务能力，保留请求、运行和审批身份；桌面与浏览器实时收敛到同一结果 |
| 项目与目录 | 路径指 B；C 上传的文件需明确落到 B，不能把 C 的路径当作 B 的文件 |
| 附件、上传、导出 | 明确大小限制、文件名处理、存放及清理；导出下载到 C 与在 B 保存应可区分 |
| 工作区删除等写操作 | 白名单逐项说明对象和影响；按既有确认与错误语义执行，不远程开放任意 IPC |
| 定时任务 | 读写同一份规则；B 的时区和执行状态为准；明确手动运行是否影响自动调度进度 |
| 原生终端 | 明确属于哪个视图、关闭清理谁、多视图冲突如何提示；不能关闭别的视图或设备运行 |
| 窗口、安装器、开发工具与凭据 | 留在桌面；浏览器不获得 A 的服务凭据，也不能指定任意上游地址 |
| 移动端交互 | 小屏消息、输入、审批、滚动和虚拟键盘实际可用；复用构建不等于自然适配手机 |

长期成本也在这里：以后加一项本机能力，应主要是在宿主适配边界决定如何暴露，而不是修改每个业务组件两遍。两端共用业务回归，再为 Web 补认证、传输和浏览器特有测试。

### 合入前的最小证据

至少覆盖 Web 未开启时的桌面完整流程、开启后的桌面与浏览器并行流程、监听失败和端口更换、撤销和过期对现存 WebSocket 的影响、跨来源请求、非法方法及参数、多个连接配置隔离、重复请求与超时、调度唯一性、终端归属与断线清理。

安全评估按真实能力做：能够发消息并批准执行，通常就已经有驱动 B 上 shell 的高权限，不能因为 API 白名单较短就宣传成低权限入口。它仍是单用户自用，不要求为这一版搭建完整角色权限系统。

因此建议作者先完善再合；若当前无法收敛，就保持讨论、分拆必要的公共改动或等待下一批。**“实验性”和“默认关闭”都不能替代对既有客户端的回归保证。**

## 线路 3：无头 Linux 客户端

### 形态和先后

```text
C：实际客户端 --控制--> A：Claude Code
                         |
                         +--执行通道--> B：无头 Linux 客户端
                                          项目、工具链、长任务

可选：C 的浏览器 --Web 鉴权--> B 的 Web 适配层
```

这里“无头”指不依赖图形显示服务器、桌面会话和 Electron 窗口，保留一个能作为 B 注册的客户端运行进程。可以称为“无头执行端”（headless execution client）；内部公共部分若需要命名，可用“客户端运行核心”（client runtime）。不要把它另叫一个 Claude 服务端而混淆 A、B。

优先走线路 1，所以 B 只需主动连 A，不必为日常控制开放新的入站端口。线路 2 是可选入口，不能反过来要求无头端必须启用 Web。技术上也可以先用 Web 操作无头端，但这不是目前的首选推进顺序。

### 由“云电脑 bot”联想到什么

讨论里“云电脑”“常驻 bot”“agent 机器”指向的共同体验是：计算环境持续存在，人通过轻入口观察、审批和追加任务。比较准确的相邻概念包括：

- **远程开发环境 / 云开发环境（remote/cloud development environment）**：项目、依赖和算力留在稳定的机器，操作入口可以换。Coder 的官方仓库将工作区、基础设施和接入方式分开描述，可以借鉴角色拆分；本项目不因此引入 Terraform 平台、团队治理或自动供给集群。
- **移动端 agent 控制（mobile agent control）**：Happy 的官方仓库包含移动与 Web 客户端、CLI 和同步中继，并描述从手机继续会话。这为“离开桌面也能看进度和发指令”提供了可对照的具体产品形态；不意味着要复制它的中继、加密架构或多人能力。
- **常驻执行进程（daemon）与聊天机器人入口**：bot 可以只是发通知、收指令的操作端，真正持有项目与执行环境的是 B。以后若接入这类入口，也应复用现有控制能力，不给每种聊天工具做一套 agent 运行逻辑；目前没有决定开发 bot 集成。
- **云电脑 / computer-use agent**：这一类词有时包含完整图形桌面与鼠标操作。本文的无头 B 首先只有开发执行环境，不自动包含 GUI、截图或桌面自动化。若未来任务需要图形环境，那是另外的执行能力。

参考的是分离人的入口与常驻工作环境的思路，不是声称这些产品与本项目架构完全相同，也不是声称已经验证“所有主流产品都如此”。A 与 B 分离正是本项目需要继续保留的特点：agent 的运行位置和重开发环境不必相同。

外部资料核对于 2026-10-14：[Coder 官方 README](https://github.com/coder/coder/blob/a4c100e5fe240afeea1cea969af8063537e00454/README.md)、[Happy 官方 README](https://github.com/slopus/happy/blob/fda37d23fa044bb03093a62bdb48a1d5689790c9/README.md)。这里只据其自述做概念对照，没有实测这些产品，也不比较性能或安全水平。

### 可复用什么，还缺什么

已有 [POSIX SSH 实现](../../apps/desktop/electron/posix-ssh.mjs)、[独立工作进程](../../apps/desktop/electron/posix-ssh-worker.mjs)、[连接桥](../../apps/desktop/electron/proxy-bridge.mjs) 和 [WSS 执行通道](../../apps/desktop/electron/tunnel-channels.mjs)，说明不是从零开发 Linux 执行能力。但“存在独立模块”与“不依赖 Electron 的可部署产品”是两回事。

需要逐项拆开：

| 部分 | 无头端要解决的问题 |
| --- | --- |
| 启动和配置 | 非交互配置 A 的地址、证书信任、设备身份、项目路径；身份重启后稳定，不靠桌面设置页 |
| 连接和重连 | Node 入口、代理配置、证书校验、隧道与优雅退出；去除必须由 Electron 提供的环境依赖 |
| 项目与运行权限 | 路径在 B 校验，以明确的普通系统用户运行；允许目录列表不等于 shell 沙箱 |
| 凭据 | 没有桌面钥匙串时采用权限受限的存储；不把秘密写进命令行、日志和分发包 |
| shell 与工具链 | 非交互服务环境中的 PATH、登录 shell、SSH agent、私有仓库访问、SFTP 和子进程回收 |
| 定时任务 | 若首版承诺支持，需将渲染页调度抽到同一套可复用运行逻辑；否则明确暂不支持，不能静默失效 |
| 运维 | 明确启动、停止、状态和日志；systemd 可作为参考部署，重启与升级行为可预测 |
| 分发 | 不带图形桌面的独立包，复用协议版本和升级契约；发行版、架构和测试矩阵逐步扩展 |

专用用户或容器可以帮助约束环境，但不自动形成强隔离。模型经 B 执行的命令拥有该运行用户能用的权限。也不应为了无头形态重新设计一套执行协议。

### 与既有 #9 和 #44 的关系

[#9](https://github.com/sun168567/cc-desk-tunnel/pull/9) 及[以前的评估](linux-client-and-tunnel.md)讨论过终端客户端、后台常驻、Linux 执行与 WSS。终端客户端给人一个交互式 CLI；无头客户端可以在完全无人操作的情况下常驻，二者可共用核心但不是同一种界面。

[#44](https://github.com/sun168567/cc-desk-tunnel/issues/44) 希望 Windows UI 机作跳板，真正执行在 Linux 开发机。它与线路 3 的需求交集是“界面机器不等于项目机器”，但提出的拓扑不同。若 Linux B 能直接连 A，线路 1 + 3 可以避免 Windows C 必须一直开着转发；若网络规定只能经 Windows 跳转，直接接入就不满足条件，仍需独立评估跳板。

#44 的字母命名与本文不同；这里按角色理解，不逐字套用。不能把新方向写成对该 issue 所有场景的已完成解决。

## 放在一起比较与分工

| 维度 | 线路 1 | 线路 2 | 线路 3 |
| --- | --- | --- | --- |
| 核心价值 | 从另一个客户端操作原开发机 | 从浏览器操作现有客户端 | 开发机不再需要图形界面 |
| 可达性前提 | B、C 都能连 A | C 能访问 B 的 Web 入口 | 优先与线路 1 相同 |
| 改动面 | 服务端、协议、客户端 | B 的 Web 适配、认证、宿主能力与打包 | 客户端运行核心、配置、进程管理与分发 |
| 主要难点 | 设备状态、归属与并发控制 | 保持桌面行为、认证、多视图一致性 | 剥离 GUI 依赖、无人值守与环境一致性 |
| 风险控制重点 | 按 B 执行、准确授权、断线与重复操作 | 可选入口隔离、失败不影响桌面、可复现回归 | 稳定身份、凭据、服务重启与进程清理 |
| 持续维护成本 | 一套 UI 与协议增加明确的设备语义 | 每项宿主能力需考虑浏览器适配 | 新增一种分发及运行环境，不能只算开发代码 |
| 当前安排 | 优先推进，邀请合作 | 作者完善后评审，可并行准备 | 保留设计，优先在 1 之后推进 |

这一轮先把共同理解记录进主线，再在 #70 回复并引用本文。邀请作者继续完善 Web，也欢迎共同做“其他设备”的状态和远程控制；不把线路 1、3 的全部工作压成 #70 的合入前提。

## 待验证与仍需决定

- 线路 1 的设备快照、通道就绪判断、无会话设备展示和远端项目来源，字段及持久化边界尚未设计。
- B/C 同时发送、审批、取消、接管，C 离开而 B 留下，B 离线又重连，均需服务端和界面回归；旧终端限制应明确保留或另案修改。
- Web 关闭与开启对桌面连接、任务、调度和退出语义的等价性尚未实测；#70 的当前公共汇聚层是否拆分、如何收敛需与作者讨论。
- Web 会话有效期、撤销粒度、监听设置保存方式、HTTP/HTTPS 部署边界和能力对照还需定稿；随机配对码可沿用，未决定必须增加自定义密码。
- 手机浏览器、小屏、跨时区、多个连接配置与多标签页行为需要真实验收；自动测试不替代这些验证。
- 无头 Linux 的独立运行依赖、定时任务位置、systemd 环境、长任务回收和分发形式尚未验证；首个支持系统与架构另行确定。
- 外部项目仅作为思路来源；没有做性能、成本或安全对标。场景常用程度和开发工作量都是研究判断，没有据此承诺发布日期。

后续实现应继续遵守[架构取舍](../architecture.md#取舍原则)：优先用现有机制和成熟组件，保持单用户、自有设备、原生 Claude Code 的边界；需要新增能力时说明实际场景与代价，而不是因为有三条路线就提前建设一个通用远程控制平台。
