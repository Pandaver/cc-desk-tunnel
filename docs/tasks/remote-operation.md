# 远程操作“其他设备”的会话：讨论留档

> 生命周期：本文件只在这项开发进行期间存在，记录讨论的前因后果、已定的决定和待定的选项，供换机器或中断后接着做。功能完成并合入 `main` 后删除本文件，把仍然有效的结论改写进 [架构](../architecture.md)、模块 README 和 [路线](../roadmap.md)。

## 由来

讨论起于 #70（桌面客户端开放 Web 入口）。评审时发现它背后的需求是：项目和开发环境留在一台机器上，人换个地方、换个设备继续操作它。整理成 [远程操作与无头执行端的研究](../research/remote-access.md)，分出三条线路：

1. 客户端之间远程操作：在“其他设备”里直接操作另一台电脑上的会话。本文件就是这一条。
2. 客户端开放 Web 入口（#70，由作者继续完善）。
3. 无头 Linux 客户端（以后）。

线路 1 与现有架构最贴合，决定优先做。为了不拖住其他改进，这一项排在下一版其余事项（长会话贴底、命令菜单、全局说明等）之后专项开发。

## 角色

- A：服务端，运行 Claude Code。
- B：会话所在的电脑，项目和执行环境在它上面。
- C：人此刻在用的另一台电脑，也装着客户端、连着同一个服务端。

目标：C 能看到 B 在不在线；B 在线时，C 可以直接操作 B 上的会话（发消息、运行中追加、审批与回答提问、停止、结束后台任务、改会话设置），命令仍在 B 上执行。现有的“在本机继续”“分叉到本机”保留，它们用于真的要换开发机器的时候。

## 现状（写本文件时的代码）

- 运行记在**发起者**的设备名下：`server.ts` 里新运行的 `device: deviceOf(peer).id`，命令走 `seats.get(run.device).door` 也就是发起者那台设备的执行通道。
- 新运行前 `onDevice` 要求会话属于发起者的设备，否则 `other_device`。
- 运行中追加消息（`message.send` 遇到 `activeRun`）、停止、结束后台任务、审批（`controlRun`）都要求 `run.device` 等于发起者设备，否则 `not_owner`。
- 服务端已经知道每台设备是否在线、执行通道是否就绪（`seats`：设备的连接集合与 `door`），但没有告诉客户端。
- 客户端用 `isHere` / `away` 区分本机与其他设备的会话；其他设备的会话不显示输入框，只显示“在本机继续…”“分叉到本机…”的提示条（`App.tsx` 的 `elsewhere-bar`）。
- 审批先到先得：第二个回复得到 `approval_inactive`（“审批已失效”）。
- 同一 `requestId` 的消息重复到达按同一条处理（`store.userMessage` 比对）。
- 设备标识是客户端自己生成并报告的随机 UUID，会话列表会把各设备的标识发给所有客户端。

## 已定的决定

1. **运行归属会话所在的设备**：运行记在 `session.device` 名下，走 B 的执行通道；指令可以来自连着同一服务的任何设备。B 离线时不能操作，C 上照旧显示现在的提示条。
2. **用户消息不改写、不标来源设备**：不论从哪台设备发，都视作在会话所在的设备上发送。用户需要 Claude 知道自己换了设备（例如让 Claude 把另一台电脑上的文件经服务端搬过来再搬回去），自己在消息里说清楚，项目不做兜底。
3. **多端同步**：事件本来就广播给订阅了该会话的所有客户端，B、C 自然看到同一份对话、审批和状态。
4. **防重复**：
   - 同一 `requestId` 重发仍是幂等的；
   - 审批和提问先到先得，后到的回复改为友好提示“已在另一台设备上处理”，不报“审批已失效”；
   - 重复的停止、结束任务视为无操作；
   - 两端同时发出的不同消息都保留，它们都是用户的真实输入；
   - 会话设置以后提交的为准，并同步给各端（现状如此）。
5. **协议版本提升**，两端同版本升级，沿用现有的升级提示。
6. **范围**：研究文档中的第一期（服务端与协议）和第二期（客户端）一起做；第三期（在 C 上为 B 的项目新建会话）不做；不做远程终端、不在 C 上浏览 B 的文件、定时任务不变。
7. 后台任务期间允许改名、编辑重发、分叉（#75 中需要服务端配合的部分）尚待评估，可视情况并入这一项的服务端改动一起测试。
8. **不做授权**：远程操作不改变安全模型，理由见下节。

## 授权（评估结论：不做）

最初设想由 B 逐一授权哪些设备可以操作自己的会话（未授权时弹窗询问、拒绝即拉黑、可允许全部），之后又评估过设备密钥绑定，以及仿照向日葵的系统账户密码、访问密码加配对令牌。进一步核对后的结论是：这些机制都改变不了安全模型，因此不做。

- **不开放远程操作时，持有服务凭据的人已经能操作所有在线设备。** 服务进程、各会话的 Claude Code、原生终端在容器里是同一个 Linux 用户（`SECURITY.md` 已写明）。各会话的 SSH 配置都在数据目录的 `session-ssh/` 下，`Include` 各设备入口的配置，里面是该设备的登录密钥与连接复用的 socket。任何一个会话里的 Claude 或原生终端，都能 `ssh -F <其他设备某个会话的配置> device-script`。服务端的 `onDevice`、`not_owner` 只约束客户端界面发来的指令。
- **加上授权以后依旧如此。** 无论名单、令牌放在服务端还是客户端，用密码还是弹窗，绕过的路径都在 SSH 这一层，不经过任何授权检查；B 只看得到从自己执行通道进来的 SSH 连接，分不清它来自哪个会话、哪台设备。
- **真正隔离的代价。** 需要按设备分 Linux 用户运行 Claude Code，拆分登录凭据、配置目录与会话记录，服务端还要有切换用户的权限。这与容器“非 root、去掉全部 capabilities”的做法和[架构](../architecture.md)中“不做多租户隔离”的原则相悖，工作量也远超这一项本身。即便做到，凭据持有者仍能经协议读到全部会话、使用 Claude 账号。
- **早期的设备锁同理。** “一个服务端只接受一台设备”在同一服务内并不改变模型，只是逼着每台设备各用一个服务、一份凭据。需要隔离的使用者仍可以这样部署，这是部署上的选择，不需要代码。
- **结论。** 远程操作没有扩大凭据泄漏的影响面，只是把已有的能力做成正当的界面功能。也不加“允许其他设备操作本机会话”的本地开关：它不防凭据泄漏，误操作的风险也不足以单设一项。
- 已据此更新 `SECURITY.md`：同一服务下的设备之间没有隔离；需要隔离就分开部署；设备在线即可被持有凭据的人操作，无人值守又不需要远程使用时退出客户端。
## 进度

- 服务端、协议和客户端已实现（协议版本沿用本版已升的 18，0.3.3 发布前不再另升），单元测试与界面测试覆盖；还没有在两台真实电脑上验证（见文末“真实环境”）。
- 实现与本文的差异：
  - 原生终端也按同一规则开放：会话所在设备在线时，别的设备可以为它打开原生终端，终端里的 Claude Code 同样经那台设备的执行通道执行。
  - 编辑重发（从某条消息之前分叉）对别的设备的会话仍不提供：分叉落在发起分叉的设备上，与“在 B 上执行”的预期不符；需要时先“在本机继续”或“分叉到本机”。
  - 执行通道还没就绪的设备在侧栏显示为离线，几秒后变为在线；不单设“连接中”状态。
  - 会话所在设备在宽限期内断开、运行尚未结束时，服务端仍接受其他设备的审批与停止，客户端此时只显示状态、不提供按钮。

## 改动点（初步）

- 协议：设备在线状态的下发（在线、执行通道就绪、离线）；后到审批的友好结果；版本提升。
- 服务端：运行归属改为会话所在设备；`onDevice`、`controlRun` 与运行中追加消息的设备校验改为“会话所在设备在线”；向客户端广播设备状态。
- 客户端：“其他设备”分组显示在线状态；选中在线设备的会话时显示输入框和“在 B 上执行”的提示，审批与停止可操作；离线时保留现有提示条。

## 参考

- tmux 多个客户端连接同一会话：会话留在主机上，谁连上都能输入，先回应的为准。
- Happy（手机控制 Claude Code 会话）、VS Code Remote Tunnels：操作入口随人走，执行环境留在原处。

## 验证计划

- 服务端单元测试：运行归属、各类设备校验、审批先到先得的友好结果、设备离线时的拒绝。
- 界面测试：用模拟服务覆盖在线、离线两种状态，以及两端同时审批、同时发消息。
- 真实环境：两台电脑连同一服务端，C 操作 B 的会话完成一次带审批的运行；运行中 B、C 各追加一条消息；B 断线与重连。
